# Sandcastle Workspace Workflow

## Purpose

This is the main workflow this project is moving toward: a user creates one local workspace for a feature, develops the feature plan with an agent, turns that plan into a PRD, breaks the PRD into implementation issues, and then lets Sandcastle run as much AFK work as possible in parallel.

The workspace remains the user's durable unit of work. Sandcastle is the execution engine for parallel and reviewable implementation slices inside that workspace.

## Target Flow

1. The user creates a workspace with a brief description.
2. The user enters a grilling session with an agent to clarify the desired feature, constraints, risks, and acceptance criteria.
3. The agent turns the clarified conversation into a PRD for the workspace.
4. The agent turns the PRD into implementation issues.
5. The user runs Sandcastle on the workspace.
6. Sandcastle identifies AFK issues whose blockers are complete and runs those issues in parallel on separate child branches.
7. Sandcastle runs an AI review after each implemented issue branch and lets the implementer iterate until the branch is acceptable.
8. Sandcastle merges completed child branches back into the workspace task branch when those merges are needed to unblock dependent tasks.
9. Sandcastle repeats until all currently unblocked AFK work is complete.
10. If a HITL issue blocks progress, the user resolves that decision or work item with an agent.
11. Sandcastle resumes and completes the remaining AFK work.
12. The workspace stops for user review after all planned task work is merged.
13. The user creates a PR from the workspace task branch.
14. Humans review the PR.
15. Review feedback is brought back into the workspace through a manual LLM intake command as follow-up issues or direct fixes.
16. Sandcastle, review agents, or the user resolve the feedback.
17. The PR is updated and merged.

## Domain Model

### Workspace

A workspace is the parent unit of work. It owns the durable metadata:

- brief captured input
- current PRD or spec
- generated issues
- notes
- repo worktree records
- GitHub and Jira snapshots
- run summaries

The workspace should outlive individual Sandcastle runs.

Each workspace also maintains a generated VS Code workspace file under the workspace root:

```text
<workspace-id>.code-workspace
```

The file includes the workspace ledger and every repo worktree recorded in `workspace.yaml`, so a user can open one editor window for the task. It is derived from the ledger and should be regenerated by workspace CRUD commands.

### Workspace Task Branch

Each repo in the workspace has one main task branch. This branch is the integration branch for the feature.

Example:

```text
TASK-123
```

All completed child work eventually merges back into this task branch.

### Issue

An issue is a slice of work produced from the PRD. Issues should be small, independently understandable, and explicit about dependencies.

Each issue should track:

- id
- title
- type: `AFK` or `HITL`
- status
- blocked-by issue ids
- acceptance criteria
- optional Sandcastle branch
- optional review result

AFK issues are safe for agents to implement without further user input. HITL issues require a human decision, product judgment, design review, credential, environment access, or other manual intervention.

Issues are local workspace artifacts first. They do not need to be GitHub issues for Sandcastle execution. GitHub issues may be added later as a publishing or synchronization target, but local workspace issues are the execution contract.

The first implementation stores issues as Markdown files under the workspace ledger:

```text
issues/
  1.md
  2.md
  3.md
```

Each file uses YAML frontmatter for machine-readable fields and Markdown body text for the work description and acceptance criteria.

### Sandcastle Child Branch

Sandcastle does not write multiple parallel agents into the workspace task branch directly. Each AFK issue runs on its own deterministic child branch.

Example:

```text
TASK-123                  # workspace task branch
sandcastle/TASK-123/1     # child branch for issue 1
sandcastle/TASK-123/2     # child branch for issue 2
sandcastle/TASK-123/3     # child branch for issue 3
```

The task branch is updated only during the merge phase.

## Execution Model

When the user says "run Sandcastle on this workspace", the runner should:

1. Read the workspace PRD and generated issues.
2. Build the issue dependency graph.
3. Select AFK issues where all blockers are complete.
4. Create one Sandcastle child branch per selected issue.
5. Run implementer agents in parallel.
6. Run a reviewer agent after each issue implementation.
7. If review fails, return the branch to the implementer or create a follow-up issue.
8. Merge completed issue branches back into the workspace task branch as needed by downstream dependencies.
9. Mark merged issues complete in the workspace ledger.
10. Recompute the dependency graph.
11. Continue until no unblocked AFK issues remain.

The dependency graph is evaluated between rounds. If issues 1 and 2 are complete, issue 3 can become eligible in the next round.

Merges do not need to wait for every AFK and HITL task in the workspace to finish. They should happen when required to make dependent tasks available or when the current batch is ready to integrate. Human review waits until all planned task work has been merged into the workspace task branch.

The first implementation exposes this through `workspace.py sandcastle <workspace-id>`. It writes a JSON run plan under `runs/` containing the selected dependency-ready AFK issues, ready HITL issues, workspace metadata, repo metadata, issue body text, and deterministic child branch names. With `--execute --command`, it runs a repo-local Sandcastle command and passes the plan path through `WORKSPACE_SANDCASTLE_PLAN`.

Only one Sandcastle execution may run for a workspace at once. The helper writes an active run lock while `--execute` is running and refuses a second execution until the first exits and releases the lock.

The repo-local runner should write a result JSON to `WORKSPACE_SANDCASTLE_RESULT`:

```json
{
  "issues": [
    {
      "id": "1",
      "status": "merged",
      "reviewStatus": "approved",
      "commits": [{ "sha": "abc123" }],
      "cleanupStatus": "pending"
    }
  ]
}
```

The workspace tool reconciles that result after execution, or later through `workspace.py sandcastle <workspace-id> --reconcile-result <result.json>`. Reconciliation updates issue frontmatter, records notes, and moves the workspace to `user-review` when every local issue is complete.

`workspace.py sandcastle <workspace-id> --init-runner` scaffolds a repo-local runner into `.sandcastle/`. The generated runner reads the plan, starts one child branch per ready AFK issue, runs an implementer, runs a reviewer, feeds `needs-fix` feedback back to the implementer for a bounded number of review cycles, and writes the result file. Approved issue branches are merged serially into the workspace task branch after the parallel implement/review pipelines finish.

If an approved child branch cannot merge cleanly, the result should preserve the child branch and mark the issue `blocked-hitl` with `reviewStatus: approved`, `mergeConflict: true`, and the merge error. Merge conflicts are not generic runner failures; they are explicit blocked work that a human or follow-up agent must resolve.

Cleanup is intentionally HITL and is primarily workspace-level. `workspace.py cleanup-plan <workspace-id>` is read-only and reports whether the whole workspace can be removed: workspace state, linked worktree safety, dirty state, open PR snapshots, unexpected files, and a recommended action. `workspace.py cleanup-plan --all --write` writes an auditable JSON plan under `ledger_root/runs/` for bulk review. The actual deletion step requires explicit approved workspace ids via `workspace.py cleanup --from-plan <plan.json> <workspace-id> ...` or the quick single-workspace form `workspace.py cleanup <workspace-id>`. Cleanup revalidates safety before removing anything and refuses stale plan entries. Cleanup removes clean linked worktrees under the workspace root and keeps the ledger. It refuses active workspaces, dirty repos, non-linked checkouts, external worktrees, unexpected files, and open PR snapshots.

Per-issue Sandcastle child branch cleanup is secondary. Use `workspace.py cleanup-plan <workspace-id> --issues` and `workspace.py cleanup --item <workspace-id>:<issue-id>` only when the user needs to prune child branches before the whole workspace is ready to remove.

## Review Loop

Sandcastle enables automatic review after each task because each issue branch has isolated context.

A typical issue pipeline is:

```text
implementer -> reviewer -> implementer fixes if needed -> merge to task branch
```

The reviewer should run in a separate agent context from the implementer. It checks the issue branch against:

- the issue acceptance criteria
- the workspace PRD
- repo conventions
- tests and verification output
- obvious regressions or missing edge cases

If the review finds problems, the branch should not be merged until the implementer fixes them or a follow-up issue is created intentionally.

Human review is separate from this per-task AI review. Human review happens after the planned task work has landed on the workspace task branch and the workspace is ready for the user to inspect or publish as a PR.

## HITL Handling

HITL issues are not failures. They are explicit pauses in the automation.

When all remaining issues are blocked by HITL work, the workspace should clearly report:

- which issue needs human input
- what decision or action is required
- which AFK issues are blocked by it

Agents may classify HITL boundaries pragmatically at first. The exact taxonomy can be tuned later. After the user resolves the HITL issue, Sandcastle can resume from the same workspace and continue with newly unblocked AFK work.

## PR Feedback Loop

Human PR review feedback should return to the same workspace rather than becoming detached context.

Feedback intake is manually triggered. The user asks an LLM command or session to read the review feedback, interpret it, and decide whether it should become follow-up issues or direct fixes. This is often itself a HITL session because PR comments can require product judgment, reviewer negotiation, or codebase-specific interpretation.

The first version does not need special feedback-intake code. The expected behavior is an agent protocol:

1. Read the workspace ledger and identify the repo, task branch, and PR snapshot.
2. Refresh PR metadata with `sync-github` if needed.
3. Inspect unresolved review threads, requested-changes reviews, actionable top-level comments, and relevant CI output.
4. Group comments by required change, not by raw comment count.
5. Classify each group as `direct-fix`, `workspace-issue`, or `HITL`.
6. Make direct fixes only when they are small and obvious.
7. Create local workspace issues for larger or independently reviewable follow-up work.
8. Create HITL issues or ask the user when feedback requires judgment or negotiation.
9. Append an intake note summarizing what was found and what was created.
10. Set the workspace state to `review-feedback` until the follow-up work is resolved and pushed.

Each created issue should retain a short reference to the original PR feedback so later agents can trace why it exists. Local issues remain the execution contract; GitHub review comments are source input, not the canonical task list.

Feedback can be handled in two ways:

- For small, obvious fixes, the agent or user can make the fix directly on the workspace task branch and update the PR.
- For larger or multi-part feedback, the agent should convert review feedback into new workspace issues, then Sandcastle can run the AFK subset the same way it handled the original implementation plan.

This keeps the review phase inside the same workflow:

```text
review feedback -> workspace issues -> Sandcastle AFK work -> update PR
```

## Constraints

- Do not run multiple agents concurrently on the same branch.
- Parallel Sandcastle work must use separate child branches and worktrees.
- The workspace task branch is the integration branch, not the parallel execution branch.
- Do not require GitHub issues for local Sandcastle execution. Local workspace issues are enough.
- GitHub issues may be used later, but the workspace ledger remains the local source of truth.
- Sandcastle should be an execution engine, not the canonical metadata store.
- Support one repo at first.
- After a child branch is merged, mark it done in the workspace ledger.
- Cleanup of child branches and worktrees is a later explicit user-triggered action, not part of the automatic merge path.

## Resume and Status

The workspace ledger should make Sandcastle runs resumable. A later run should be able to inspect local artifacts and decide:

- which issues are planned
- which issues are blocked
- which issues are running or need review
- which issues have been reviewed
- which issues have been merged
- which child branches exist
- which child branches are done but not cleaned up

The first issue status vocabulary is:

```text
planned
ready
running
reviewing
needs-fix
blocked-hitl
merged
done
failed
skipped
```

The vocabulary can evolve, but the system needs enough durable state to resume without relying on conversation memory.

## Success Criteria

This workflow is successful when a user can:

- capture a rough feature idea in a workspace
- clarify it through a grilling session
- generate a workspace PRD
- generate dependency-aware AFK and HITL issues
- run Sandcastle to complete all currently unblocked AFK work
- pause cleanly for HITL work
- resume Sandcastle after HITL work is resolved
- produce a PR from the workspace task branch
- turn PR feedback into either direct fixes or follow-up issues
- use Sandcastle again to resolve review feedback
- merge the PR with the workspace ledger still reflecting what happened

## Deferred Automation

The workflow may later grow a `feedback-intake` command that fetches review-thread metadata and writes a draft intake report. That is not required for V1. Until repeated manual intake becomes painful, the LLM protocol plus `sync-github`, `note`, `state`, and `issue create` is enough.
